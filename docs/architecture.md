# Architecture

## Current MVP Architecture

```text
CSV Retail Dataset
        ↓
Python ingestion pipeline
        ↓
Validation and column normalization
        ↓
PostgreSQL raw layer
        ↓
Ingestion metadata tracking
        ↓
dbt staging layer
        ↓
dbt marts layer
        ↓
Analytics-ready tables
        ↓
SQL analysis / Metabase dashboard
````

## Implemented Components

| Component                  | Status    | Notes                                                      |
| -------------------------- | --------- | ---------------------------------------------------------- |
| CSV ingestion              | Completed | Implemented with Python and pandas                         |
| Raw PostgreSQL schema      | Completed | Uses `raw` schema for source-like tables                   |
| Ingestion metadata         | Completed | Uses `metadata.ingestion_runs`                             |
| Required column validation | Completed | Validates source files before loading                      |
| Primary key validation     | Completed | Checks null primary keys and composite keys                |
| Column normalization       | Completed | Standardizes source column names                           |
| Idempotent reload          | Completed | Uses `TRUNCATE + INSERT` for MVP batch reload              |
| dbt raw sources            | Completed | Sources defined for raw tables                             |
| dbt staging models         | Completed | Cleans, renames, and casts raw data                        |
| dbt marts                  | Completed | Includes core dimension/fact models and analytics marts    |
| SQL practice queries       | Completed | Includes joins, CTEs, window functions, and quality checks |
| Metabase dashboard         | Planned   | Dashboard integration is a future improvement              |
| Airflow orchestration      | Planned   | Not implemented in current MVP                             |
| GitHub Actions CI/CD       | Planned   | Not implemented in current MVP                             |
| AWS-ready docs             | Planned   | Not implemented in current MVP                             |

## Schema Separation

| Schema            | Purpose                                                           |
| ----------------- | ----------------------------------------------------------------- |
| `raw`             | Stores raw CSV data loaded into PostgreSQL                        |
| `metadata`        | Stores operational metadata for ingestion runs                    |
| dbt target schema | Stores staging, dimension, fact, and mart models generated by dbt |

## Data Flow

### 1. Ingestion Layer

The ingestion layer reads CSV files, validates required columns and primary keys, normalizes column names, and loads data into PostgreSQL raw tables.

```text
data/raw/*.csv
        ↓
ingestion/load_csv_to_postgres.py
        ↓
raw.raw_customers
raw.raw_orders
raw.raw_order_items
raw.raw_products
raw.raw_payments
raw.raw_shipments
```

### 2. Metadata Tracking

Each ingestion attempt is tracked in:

```text
metadata.ingestion_runs
```

This table helps debug pipeline runs by storing source name, target table, row count, status, start time, finish time, and error message.

### 3. dbt Modeling Layer

dbt transforms raw data into analytics-ready models.

```text
raw tables
        ↓
staging models
        ↓
core marts: dimensions and facts
        ↓
analytics marts
```

Current dbt staging models:

```text
stg_customers
stg_orders
stg_order_items
stg_products
stg_payments
stg_shipments
```

Current core marts:

```text
dim_customers
dim_products
fact_orders
fact_order_items
```

Current analytics marts:

```text
mart_daily_revenue
mart_product_performance
mart_delivery_performance
```

## Current Design Decision

The current MVP intentionally focuses on a simple but explainable ELT flow:

```text
raw → staging → marts
```

An intermediate layer is not implemented yet. For this MVP, business logic is still small enough to keep inside marts. If the project grows, an intermediate layer should be added to separate reusable joins and business logic from final reporting marts.

## Why This Design?

This design separates ingestion, storage, transformation, and analytics outputs. It makes the pipeline easier to debug, test, explain in interviews, and extend later with Airflow, CI/CD, dashboards, and AWS deployment notes.

# Data Quality Strategy

## Goal

The goal of the data quality strategy is to prevent invalid data from silently entering the warehouse and to make data issues easier to detect, debug, and explain.

This project currently uses three levels of checks:

```text
Python ingestion validation
        ↓
dbt model tests
        ↓
manual SQL data quality checks
````

---

## 1. Python Ingestion Validation

The ingestion layer validates source files before loading them into PostgreSQL.

| Check                       | Purpose                                               |
| --------------------------- | ----------------------------------------------------- |
| File existence check        | Prevent loading missing input files                   |
| Required column validation  | Ensure source files contain expected columns          |
| Primary key null validation | Prevent invalid primary keys                          |
| Composite key validation    | Validate tables such as order items and payments      |
| Column name normalization   | Standardize column names before loading               |
| Idempotent reload           | Avoid duplicated rows when rerunning the pipeline     |
| Ingestion run tracking      | Record success/failure, row count, and error messages |

If validation fails, the pipeline records the failure and exposes the error through logs and `metadata.ingestion_runs`.

---

## 2. dbt Tests

dbt tests are used to validate transformed models.

Current test types:

```text
not_null
unique
relationships
accepted_values
```

Example command:

```bash
cd dbt
dbt test --profiles-dir .
```

Current test coverage focuses on critical identifiers and relationships, such as:

```text
order_id
customer_id
product_id
order_item_key
payment_key
order_status
```

## Core SQL Quality Checks

### Duplicate orders

```sql
SELECT
    order_id,
    COUNT(*) AS record_count
FROM raw.raw_orders
GROUP BY order_id
HAVING COUNT(*) > 1;
```

### Orders with missing customer IDs

```sql
SELECT COUNT(*) AS null_customer_id_count
FROM raw.raw_orders
WHERE customer_id IS NULL;
```

### Orphan order items

```sql
SELECT
    oi.order_id,
    COUNT(*) AS orphan_item_count
FROM raw.raw_order_items AS oi
LEFT JOIN raw.raw_orders AS o
    ON oi.order_id = o.order_id
WHERE o.order_id IS NULL
GROUP BY oi.order_id;
```

### Orphan product references

```sql
SELECT
    oi.product_id,
    COUNT(*) AS orphan_item_count
FROM raw.raw_order_items AS oi
LEFT JOIN raw.raw_products AS p
    ON oi.product_id = p.product_id
WHERE p.product_id IS NULL
GROUP BY oi.product_id;
```

### Negative item price

```sql
SELECT *
FROM raw.raw_order_items
WHERE price < 0;
```

### Negative payment value

```sql
SELECT *
FROM raw.raw_payments
WHERE payment_value < 0;
```

### Delivered date before purchase date

```sql
SELECT
    o.order_id,
    o.order_purchase_timestamp,
    s.delivered_customer_date
FROM raw.raw_orders AS o
JOIN raw.raw_shipments AS s
    ON o.order_id = s.order_id
WHERE s.delivered_customer_date < o.order_purchase_timestamp;
```

## Interview Explanation

A concise explanation:

> I implemented data quality at multiple layers. At ingestion time, the pipeline validates file existence, required columns, primary keys, and composite keys before loading data. dbt tests then validate transformed staging and mart models using not_null, unique, relationships, and accepted_values tests. I also added manual SQL quality checks for duplicates, nulls, orphan keys, negative values, and inconsistent delivery dates. This helps ensure the warehouse outputs are reliable for revenue, product, and delivery analysis.

# Trade-offs

This document explains the main technical trade-offs made in the current MVP.

---

## 1. Batch ELT Instead of Streaming

### Current choice

```text
CSV files → Python ingestion → PostgreSQL → dbt
````

### Why this choice?

The current project is designed as a batch ELT warehouse MVP. Batch processing is easier to build, test, debug, and explain for a first Data Engineering portfolio project.

### Trade-off

| Benefit                       | Limitation                                            |
| ----------------------------- | ----------------------------------------------------- |
| Simple and reliable for MVP   | Not real-time                                         |
| Easy to rerun locally         | No event streaming                                    |
| Good for SQL/dbt practice     | No Kafka/Spark coverage                               |
| Easy to explain in interviews | Limited scalability compared with distributed systems |

### Future improvement

Add Airflow scheduling first. Add streaming only in Project 2.

---

## 2. PostgreSQL Instead of Cloud Warehouse

### Current choice

The current MVP uses PostgreSQL as the warehouse database.

### Why this choice?

PostgreSQL is easy to run locally with Docker, supports SQL well, integrates with dbt, and is suitable for an intern/fresher-level portfolio project.

### Trade-off

| Benefit                 | Limitation                                  |
| ----------------------- | ------------------------------------------- |
| Easy local setup        | Not a cloud-native analytical warehouse     |
| Works with dbt-postgres | Limited large-scale analytics performance   |
| Good for SQL practice   | No native separation of storage and compute |
| No cloud cost           | Does not demonstrate AWS/GCP deployment yet |

### Future improvement

Add AWS-ready architecture notes later, mapping PostgreSQL to RDS PostgreSQL, Redshift, or Athena depending on target design.

---

## 3. TRUNCATE + INSERT Idempotency

### Current choice

```text
TRUNCATE target raw table
        ↓
INSERT latest CSV data
```

### Why this choice?

For small batch CSV datasets, `TRUNCATE + INSERT` is simple, deterministic, and easy to reason about. Rerunning the pipeline does not append duplicate rows.

### Trade-off

| Benefit                          | Limitation                                 |
| -------------------------------- | ------------------------------------------ |
| Very simple to implement         | Reloads the whole table                    |
| Prevents duplicate append issues | Not efficient for large datasets           |
| Easy to debug                    | Not suitable for near-real-time pipelines  |
| Good for MVP                     | Does not preserve row-level change history |

### Future improvement

Add incremental loading after the MVP is stable.

---

## 4. Raw → Staging → Marts Without Intermediate Layer

### Current choice

The current dbt project uses:

```text
raw → staging → marts
```

### Why this choice?

The current business logic is still small. Adding an intermediate layer too early would increase complexity without much benefit.

### Trade-off

| Benefit                | Limitation                                  |
| ---------------------- | ------------------------------------------- |
| Simple dbt structure   | Some business logic lives directly in marts |
| Easy to understand     | Less reusable transformation logic          |
| Faster to complete MVP | Harder to scale if mart logic grows         |

### Future improvement

Add intermediate models such as:

```text
int_order_items_enriched
int_order_payments
int_customer_orders
int_delivery_performance
```

---

## 5. Basic Marts Before Full Star Schema

### Current choice

The MVP includes:

```text
dim_customers
dim_products
fact_orders
fact_order_items
mart_daily_revenue
mart_product_performance
mart_delivery_performance
```

### Why this choice?

These models are enough to tell a clear business story around revenue, product performance, and delivery performance.

### Trade-off

| Benefit                         | Limitation                              |
| ------------------------------- | --------------------------------------- |
| Strong enough for MVP demo      | Missing `dim_dates` and `dim_sellers`   |
| Easy to explain in interviews   | No customer retention mart yet          |
| Provides dashboard-ready tables | No SCD Type 2 or incremental models yet |

### Future improvement

Add:

```text
dim_dates
dim_sellers
mart_customer_retention
SCD Type 2 snapshot for products
incremental mart_daily_revenue
```

---

## 6. Manual SQL Checks Before Automated Quality Gates

### Current choice

The project includes SQL files for manual data quality checks and interview practice.

### Why this choice?

Manual SQL checks are useful for understanding the data, debugging issues, and preparing for interviews. They are also easier to build before adding Airflow or CI/CD.

### Trade-off

| Benefit                           | Limitation                 |
| --------------------------------- | -------------------------- |
| Great for learning and interviews | Not automatically enforced |
| Easy to inspect and explain       | Requires manual execution  |
| Helps validate business logic     | No automatic alerting      |

### Future improvement

Convert critical manual SQL checks into dbt singular tests and CI quality gates.

---

## 7. Metabase Planned, Not Yet Implemented

### Current choice

The current project prepares analytics marts but does not yet include a finished Metabase dashboard.

### Why this choice?

The priority is to first build a reliable warehouse foundation. Dashboarding should come after ingestion, dbt models, and data quality checks are stable.

### Trade-off

| Benefit                               | Limitation                              |
| ------------------------------------- | --------------------------------------- |
| Keeps MVP focused on Data Engineering | No visual dashboard yet                 |
| Avoids dashboard-first project smell  | Fewer screenshots for recruiters        |
| Prioritizes pipeline correctness      | Business storytelling needs more polish |

### Future improvement

Build a small Metabase dashboard with:

```text
daily revenue
total orders
average order value
top product categories
late delivery rate
average delivery days
```

---

## Summary

The current MVP is intentionally scoped for fast portfolio delivery:

```text
simple batch ingestion
clear raw/staging/mart layers
basic dimensional modeling
manual and dbt data quality checks
analytics-ready outputs
```

The project avoids overclaiming unfinished features such as Airflow, CI/CD, AWS deployment, SCD Type 2, and incremental models. These are listed as future improvements and should only be moved to completed status after they are implemented.
